# Voice Input macOS GUI 方案

## 为什么现在需要 GUI

Voice Input 已经有一套能工作的本地语音输入流程。它可以从麦克风取得音频，用本地 Whisper 模型完成识别，再把文字写进当前输入框。现在生效的配置使用 `small-q5_1` 模型、中文语言提示和 Fn 按住说话。模型下载、完整性校验、延迟记录、服务安装和故障诊断也已经有了命令行入口。

这套能力适合开发阶段，也足够证明本地方案能跑通。普通用户仍然很难判断它有没有启动、模型是否加载完成、权限缺了哪一项。第一次使用还要面对麦克风、辅助功能和输入监控三类 macOS 权限。服务停在 `starting` 时，命令行能提供线索，用户眼前却没有清楚的反馈。

GUI 的价值就在这里。它要把后台真实状态翻译成用户看得懂、能立即处理的信息。CLI 会继续保留，负责自动化、测试和深度诊断。日常使用交给菜单栏应用。

## 产品形态

Voice Input 适合做成常驻 macOS 菜单栏的轻量应用。它平时不占 Dock，也不要求用户一直开着设置窗口。菜单栏图标承担最常用的状态提示和控制，设置窗口只在首次引导、模型管理和配置调整时出现。

菜单栏图标需要表达五种状态。

| 状态 | 用户看到的反馈 | 可以执行的动作 |
| --- | --- | --- |
| 未就绪 | 灰色图标和缺失原因 | 打开权限或下载模型 |
| 就绪 | 常亮图标 | 按住 Fn 开始说话 |
| 录音中 | 呼吸动画和录音时长 | 松开 Fn 或取消 |
| 识别中 | 轻量进度动画 | 等待或取消本次识别 |
| 出错 | 红色提示点 | 查看原因并重试 |

菜单展开后只保留高频操作。用户可以暂停语音输入、打开设置、查看最近一次结果和退出应用。技术日志、模型摘要和性能统计放进诊断页面，避免日常菜单变成运维面板。

## 第一次使用

首次启动应当用一个短流程完成准备工作。

1. 说明音频默认留在本机，远程 LLM 只有在用户主动配置后才会启用。
2. 请求麦克风权限，并在用户拒绝时提供系统设置入口。
3. 请求辅助功能和输入监控权限，解释它们分别用于文字写入和 Fn 热键。
4. 检查本地模型。已有模型直接复用，没有模型时展示 fast、balanced 和 quality 三档选择。
5. 让用户在测试输入框中按住 Fn 说一句话，现场完成录音、识别和插入。
6. 测试成功后询问是否登录时自动启动。

权限请求必须跟在用户动作之后。界面应当显示系统当前返回的真实状态，不能因为应用已经发起请求就显示为成功。用户以后关闭权限，菜单栏也要回到未就绪状态，并给出准确入口。

## 日常交互

就绪以后，主流程保持简单。

用户把光标放进任何可编辑区域，按住 Fn 开始说话，松开后结束录音。应用先播放短提示音，再进行本地识别。识别完成后优先通过辅助功能直接写入文字。目标应用不支持直接写入时，继续使用已有的剪贴板保护回退方案。

界面文案保持短而具体。

- 就绪时显示“按住 Fn 说话，松开后输入文字”。
- 录音时显示“正在听”。
- 识别时显示“正在本机识别”。
- 权限缺失时显示“需要麦克风权限”或“需要辅助功能权限”。
- 模型首次加载时显示“正在准备本地模型，第一次可能需要十几秒”。
- 远程润色关闭时显示“文字不会发送到 LLM 服务”。

一次识别失败不应让整个应用退出。菜单栏保留错误原因和重试入口，后台恢复到就绪状态。连续启动失败、模型损坏和权限被拒绝需要进入诊断页面，不能只写进日志。

## 设置窗口

设置窗口分成四页已经足够。

### 常规

用户可以更换按住说话的热键，控制提示音，选择登录时启动，并暂停或恢复后台输入。Fn 与系统表情、系统听写冲突时，界面给出键盘设置入口。

### 语音识别

这一页管理语言、模型和本地识别参数。普通用户看到 fast、balanced 和 quality 三档，以及下载大小、适用场景和当前占用。线程数、VAD 阈值和提示词收进高级设置。切换模型前先完成下载与 SHA-256 校验，成功后再修改活动配置。

### 文本处理

默认使用原始 ASR 结果，不产生网络请求。用户可以连接本机 OpenAI-compatible 服务，也可以显式启用 HTTPS 远程地址。界面只保存环境变量名称或系统钥匙串引用，不能把 API Key 明文写进配置文件。连接测试需要展示耗时、模型名和失败原因。

### 诊断

诊断页展示当前版本、模型路径、权限状态、音频设备、服务状态和最近一次分阶段延迟。用户可以复制一份去除密钥的诊断报告，也可以打开日志目录。CLI 的 `doctor`、`status` 和 `benchmark` 继续作为这一页的数据来源。

## 技术结构

GUI 应当保持薄。音频、VAD、Whisper、文本修整、文字写入和指标统计继续留在 Rust 核心，SwiftUI 只负责界面、系统权限引导和 macOS 应用生命周期。

```text
Voice Input.app
├── SwiftUI menu bar and settings
├── permission and login item management
└── Rust voice core
    ├── audio and VAD
    ├── Whisper ASR
    ├── optional LLM refiner
    ├── text injection
    └── metrics and status
```

现有手写 LaunchAgent 可以在过渡期继续使用。GUI 稳定后，应由标准 macOS 应用生命周期和 `SMAppService` 管理登录项。应用签名、Bundle ID 和权限主体保持一致，避免开发态可用、安装后重新请求权限的情况。

Rust 核心需要继续维持清晰边界。产品名、菜单文案和图标只出现在应用层。ASR、音频和 LLM 模块不读取 GUI 状态，也不依赖 SwiftUI。CLI 与 GUI 共享同一份配置模型和运行状态协议。

## 第一版范围

第一版 GUI 只解决启动、权限、状态和基本设置。

- 菜单栏图标与五种运行状态
- 开始、暂停、重启和退出
- 麦克风、辅助功能、输入监控的首次引导
- Fn 热键与提示音设置
- 模型列表、下载进度、校验和切换
- 当前语言和本地识别状态
- 最近一次文字与分阶段延迟
- 日志和诊断报告入口
- 登录时启动

第一版不做云端账号、跨设备同步、团队管理和长期语音历史。默认不保存原始音频。识别历史如果以后加入，需要单独的开关、保留期限和一键清除能力。

## 验收标准

新用户在不打开终端的情况下，应当能完成安装、权限授权、模型准备和第一次语音输入。应用重启后能够准确恢复配置，并在权限或模型失效时给出可执行的原因。菜单栏显示的状态必须与 Rust 运行态一致，不能把进程存在当作服务就绪。

已有的 26 个 Rust 测试、Clippy 和交叉编译检查继续作为核心门槛。GUI 还需要覆盖首次引导、权限拒绝后恢复、模型下载中断、Fn 完整按压流程和常见目标应用的插入测试。真实延迟继续按录音、ASR、文本处理和写入分段记录。

`Voice Input` 仍是中性工程名。正式发布前需要确定产品名称、图标、Bundle ID 和签名身份。工程结构已经把这些标识集中在应用层，改名不应触及语音识别核心。
